# 网页游戏数据自动发布

2026-10-10 修复前，服务器每 6 小时更新 `/data`，网页只比较差异并提示；计算核心、原生求解器数据和活动 #1 的固定引用没有自动更新。

现在的链路：已有游戏更新器解码 Master → 将 76 张公开 Master 表和数据版本复制给网页构建机 → 同步快照与来源校验信息 → 用钉住的参考实现复核、转换谱面 → 为当前活动生成收益数据 → 同时构建 Python 运行时与浏览器原生数据 → 校验 → 先发布资源，最后替换入口页 → 同步第二台服务器。

活动选择按 Asia/Shanghai 的开始时间选择最近已经开始的活动，不依赖表内顺序或固定编号。挑战歌曲、谱面、乐曲加成和奖励均使用这个活动编号。旧计算缓存随模型内容哈希失效，玩家卡库保持。

东京构建目录 `/opt/ournotes-web-builder/source`。输入仅含解码后的公开游戏表，不含登录凭证、SDK 请求或用户账号包。独立 Node 22.14.0 与 Python 虚拟环境不替换 bot 的 Node。

阿里云任务 `/home/admin/bot/tools/update_frontend_from_master.sh`；计划 `/etc/cron.d/ournotes-auto-frontend`，服务器时间 01:10、07:10、13:10、19:10。在原有 00:45 等主数据更新、00:55 等公共数据发布后执行。共用重任务锁；东京单独有发布锁，Node 堆上限 384 MiB。日志 `/var/log/ournotes-auto-frontend.log`。

相关代码：`tools/sync_decoded_master.py`、`browser/snapshot_release.py`、`tools/auto_publish_frontend.py`、`tools/validate_snapshot_release.py`。

发布校验覆盖原始表来源哈希、运行时与原生数据来源一致、曲目/谱面数量、当前活动、挑战曲清单，以及每首活动曲的谱面和综合力构造。损坏或不支持的新数据会终止发布；相同数据及构建代码跳过重建。已有打开的页面需要刷新才能加载新版本。

备份目录 `/var/backups/ournotes-auto-frontend/<UTC时间>`，保留被替换文件。旧哈希资源保留，供旧标签页使用。后续修改网页源码时需要同步构建机源代码；定时任务只自动跟进游戏数据，不自动拉取 GitHub 源码。

实测：活动 #2「拜托了，倾心一掷」、88 首歌、352 张谱面；活动歌曲 100076、100110、100111。全部谱面与参考转换结果一致，浏览器本地歌榜组卡计算完成。未验证新活动的实机奖励结算。
